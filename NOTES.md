# NOTES.md — решения, допущения, обоснование индексов

## Стек и структура

- **Backend**: .NET 8, ASP.NET Core, MediatR 12 (пайплайн-поведение для валидации), FluentValidation,
  официальный драйвер MongoDB.Driver. Без ORM.
- **Frontend**: Vite + React 18 + TypeScript, `@tanstack/react-query` для серверного состояния.
  Выбор react-query: состояние в задаче — почти целиком серверное (списки, отчёты, мутации);
  react-query даёт кэш, повторные запросы и инвалидацию без своего стора. Держать ради этого
  mobx/redux не было смысла.
- **Проекты**: `Domain` (сущности), `Application` (MediatR-обработчики, правила, DTO, коды ошибок),
  `Infrastructure` (подключение Mongo, индексы, seeder), `Api` (тонкие контроллеры, middleware),
  `UnitTests`.

## Ключевые решения

### 1. Стоимость считается «живьём» по ставке на дату записи
Ставка не замораживается в записи. Резолв: последняя ставка с `from <= дата записи`.
Это единственный способ выполнить приёмочный сценарий 8 (сменили ставку с 01.03.2026
с 600 на 650 ₽/ч — запись 05.03.2026 пересчиталась в 5200 ₽ без правки записей).
Одинаковый резолв используется и в отчёте (в пайплайне), и в списке, и в итогах.

### 2. Отчёт — агрегация на стороне MongoDB
Требование задания: не выгружать миллионы записей в память. Пайплайн:
`$match` по диапазону месяца → `$lookup` ставки сотрудника (под-пайплайн с `$unwind rates`,
`$lte from <= date`, `$sort desc`, `$limit 1`) → `$project cost = hours × rate` →
`$group` по `projectId` (суммы часов и стоимости) → `$lookup` проекта →
проценты/признаки и `$round` до копеек считаются в пайплайне.
В память попадают только строки проектов + итоговая строка (сумма по уже агрегированным
группам, а не по сырым записям). Записи, у которых на дату нет ставки, в отчёте пропускаются
(по правилу 1 их быть не может; зафиксировано как допущение ниже).

### 3. Список — реальная пагинация на стороне БД
`Find` с фильтрами (`year/month/employeeId/projectId`) + `sort + skip/limit` + `countDocuments`.
ФИО, шифр проекта, ставка и стоимость дособираются только для текущей страницы.
Флаг переработки (день > 12 ч) считается отдельной агрегацией по полному дню сотрудника —
без фильтра по проекту и без пагинации, иначе при фильтре по проекту флаг был бы неверным.
**Итоги** (часы и стоимость по отфильтрованному списку) — отдельная агрегация с теми же
фильтрами и тем же резолвом ставки, по всей выборке, а не по странице.

### 4. Транзакции для записи
Create/update/delete выполняются в транзакции MongoDB (поэтому в compose mongo —
однонодовый replica set `rs0`). Внутри транзакции атомарно проверяются: закрытый период,
наличие ставки на дату, границы периода проекта, суточный лимит 24 ч. Драйвер сам повторяет
транзакцию при transient-ошибках.

### 5. Оптимистичная блокировка
У записи есть `Version`. При изменении клиент передаёт `expectedVersion`; если версия не
сошлась — `409 ENTRY_VERSION_CONFLICT` с внятным текстом. При конкурентной записи в тот же
документ транзакция второго участника получает WriteConflict и перечитывает запись — видит
новую версию и отдаёт конфликт.

### 6. Флаг переработки вычисляется, а не хранится
`День сотрудника > 12 ч` — производное от суммы часов за день. Хранение потребовало бы
синхронизации при каждом изменении/удалении; вычисление исключает рассинхрон.

### 7. Деньги — decimal, округление до копеек
Денежные поля — `decimal`, в Mongo — Decimal128. Округление `Math.Round(x, 2, AwayFromZero)`
и `$round` в пайплайне (оба — от нуля, как принято для рублёвых сумм). `double` используется
только для часов (деньги это не деньги).

### 8. Даты — календарные, UTC-полночь
Клиент присылает «YYYY-MM-DD». Бэкенд трактует её как календарную и хранит UTC-полночь того же
дня (`Dates.CalendarDateToUtc`), не сдвигая на часовой пояс сервера (иначе день «уезжал» бы).

### 9. Валидация входа отделена от бизнес-правил
Форма запроса (обязательные поля, диапазоны year/month/page) — FluentValidation, выполняется
в `ValidationBehavior` (MediatR pipeline) до обработчика. Бизнес-правила — чистые классы
в `Application/Rules`, тестируются юнит-тестами без БД.

### 10. Ошибки
`{ "code": "MACHINE_CODE", "message": "человекочитаемый текст на русском" }`.
400 — валидация и правила, 409 — конфликт версии и закрытый период, 404 — не найдено.
Никогда 500 с голым исключением (неожиданное — 500 с общим текстом + лог).

## Индексы (создаются на старте, `IndexSetup`)

| Коллекция | Индекс | Под какие запросы |
|---|---|---|
| `time_entries` | `{ date: 1 }` | диапазон месяца для списка и отчёта |
| `time_entries` | `{ employeeId: 1, date: 1 }` | дневные тоталы сотрудника (правила 2–3) и фильтр списка по сотруднику |
| `time_entries` | `{ projectId: 1, date: 1 }` | фильтр списка по проекту |
| `projects` | `{ code: 1 }` (unique) | уникальность шифра проекта |
| `closed_periods` | `{ year: 1, month: 1 }` (unique) | проверка «закрыт ли период» и уникальность пары |

Резолв ставки в отчёте/итогах идёт по `_id` сотрудника (`$lookup`) — индексация бесплатна.

## Допущения

1. **Смена ставки** — upsert по дате начала: если ставка на дату уже есть — меняется её значение,
   иначе добавляется новая. Одна ставка на дату. Значение влияет на все записи от этой даты до
   следующей ставки. Сценарий 8 «изменить 01.03.2026 с 600 на 650» — это смена значения.
2. **Endpoints-дополнение**: `PUT /api/employees/{id}/rates` в спеке API отсутствует, но без него
   не выполнить приёмочный сценарий 8 (смена ставки задним числом). Сознательно добавлен.
3. **Итоги списка** — по всей отфильтрованной выборке (агрегацией), а не по текущей странице.
4. **Бюджет = 0**: процент освоения `null` (в UI «—»), флаги перерасхода/риска `false`.
5. **Закрытый период при переносе записи** проверяется и по старой, и по новой дате.
6. **Отчёт** показывает только проекты с трудозатратами в выбранном месяце.
7. **Удаление** — без обязательной версии (спека требует оптимистичную блокировку только для
   изменения); удаление по id после проверки закрытого периода.
8. **Аутентификация** отсутствует (по заданию); служебные поля `CreatedBy/UpdatedBy` = «demo».
9. **Перемещение даты начала ставки назад** может «осиротить» существующие записи (у них не станет
   ставки на дату). Такие записи исключаются из отчёта/итогов (по правилу 1 их создавать нельзя).
   В UI изменение ставок не предусмотрено — проверяется через API.

## Что не доделано / что сделал бы иначе

1. **Гонка суточного лимита 24 ч.** Транзакции дают snapshot-изоляцию, но две параллельные записи
   на одного сотрудника в один день теоретически могут прочитать одну и ту же сумму и обе пройти.
   Для полной атомарности — отдельная коллекция-счётчик `(employeeId, date)` с условным `$inc`
   и unique-индексом. В задании конкуренция проверяется на редактировании записи (версия),
   поэтому выбран простой путь; счётчик — вариант «сделал бы иначе» при росте нагрузки.
2. **`$lookup` ставки в отчёте** выполняется на каждую запись (под-пайплайн по `_id`). Сотрудников
   мало, поэтому приемлемо; альтернатива — один `$lookup` всех сотрудников и резолв в пайплайне.
3. **Пагинация `skip/limit`** — при очень глубоких страницах и миллионах записей лучше
   cursor/keyset-пагинация. По требованию достаточно реальной DB-пагинации, поэтому `skip/limit`.
4. **Нет интеграционных тестов API и e2e** — только юнит-тесты бизнес-правил (задание требует
   минимум пять; сделано 40). Приёмные сценарии проверены вручную через HTTP.
5. **UI без компонентной библиотеки** — задание это разрешает, дизайн не оценивается.
6. **Список/отчёт не кэшируются** на бэкенде; при нескольких миллионах записей стоит подумать
   о кэше отчёта (ставки меняются редко). Не делал — вне требований.
7. **Идемпотентный seeder** перезаполняет базу только если она пуста; чтобы «сбросить» данные —
   нужно удалить БД (см. README).
