# Основные решения

1. Расчёт стоимости
Ставка берётся на дату записи (последняя ставка, действующая до этой даты).
Это позволяет пересчитывать старые записи при изменении ставки (например, с 01.03.2026).

2. Отчёт строится агрегацией в MongoDB
Не выгружаются все записи в память.
Агрегация: выборка за месяц → подстановка ставки → вычисление стоимости → группировка по проектам → получение данных проекта.
В память попадают только итоги по проектам и общая строка.

3. Список — настоящая пагинация в БД
Фильтры (год/месяц/сотрудник/проект) + сортировка + skip/limit.
Флаг переработки (>12 ч в день) считается отдельно по полному дню сотрудника (без пагинации).
Итоги (часы и стоимость) считаются агрегацией по всем отфильтрованным записям.

4. Транзакции для записи
Create/update/delete выполняются в транзакции MongoDB (replica set).
Внутри проверяются: закрытый период, наличие ставки, границы проекта, суточный лимит 24 ч.

5. Оптимистичная блокировка
У записи есть Version. При изменении передаётся ожидаемая версия; при несовпадении — ошибка 409.

6. Флаг переработки вычисляется, а не хранится
Считается как сумма часов за день сотрудника, чтобы избежать рассинхрона.

7. Деньги — decimal, округление до копеек
Все суммы округляются по правилу AwayFromZero.

8. Даты — календарные, хранятся как UTC-полночь
Клиент присылает YYYY-MM-DD, бэкенд превращает в UTC-полночь без смещения по часовому поясу.

9. Валидация разделена на входную и бизнес-правила
Вход (обязательность, диапазоны) — FluentValidation.
Бизнес-правила — отдельные классы, покрыты юнит-тестами.

10. Ошибки
Все ошибки возвращают код и понятное сообщение на русском.
400 — валидация, 409 — конфликт, 404 — не найдено, 500 — только для неожиданных ошибок (с логом).

11. Суточный лимит 24 ч — через отдельный счётчик
Коллекция day_counters с уникальным индексом {employeeId, date}.
При изменении записи счётчик обновляется атомарно в той же транзакции.
Это предотвращает гонку (две параллельные транзакции не смогут превысить лимит).

# Индексы (создаются при старте)

| Коллекция | Индекс | Для чего |
|-----------|--------|----------|
| `time_entries` | `{ date: 1, _id: 1 }` | Пагинация и выборка за месяц |
| `time_entries` | `{ employeeId: 1, date: 1 }` | Фильтр по сотруднику и подсчёт дневных часов |
| `time_entries` | `{ projectId: 1, date: 1 }` | Фильтр по проекту |
| `projects` | `{ code: 1 }` (unique) | Уникальность шифра |
| `day_counters` | `{ employeeId: 1, date: 1 }` (unique) | Атомарный лимит 24 ч |
| `closed_periods` | `{ year: 1, month: 1 }` (unique) | Проверка закрытых периодов |

# Допущения

1. Ставка — одна на дату, изменение ставки на дату обновляет её значение.
2. Добавлен эндпоинт PUT /api/employees/{id}/rates (не был в спеке, но нужен для сценария 8).
3. Итоги списка считаются по всей отфильтрованной выборке, а не по странице.
4. Если бюджет проекта = 0, процент освоения не показывается (—), флаги перерасхода/риска — false.
5. При переносе записи проверяется закрытый период и для старой, и для новой даты.
6. В отчёт попадают только проекты с трудозатратами в выбранном месяце.
7. Удаление выполняется без версии (только проверка закрытого периода).
8. Аутентификация отсутствует, служебные поля заполняются «demo».
9. Если при изменении ставки записи остаются без ставки, они исключаются из отчётов (такие создавать нельзя).

# Что не сделано / можно улучшить
- Пагинация skip/limit — при огромных данных лучше keyset-пагинация, но по условию достаточно.
- Нет интеграционных тестов API (только юнит-тесты, их >40).
- Кэширование отчёта не реализовано.
